# Docker Image Review: технічний PM-чек-лист

Мета: перевірити здане Docker-рішення не за фактом "зроблено", а за ознаками, які AI PM може підтвердити сам або попросити показати. Кожен пункт посилається на критерій з [`acceptance_criteria.md`](acceptance_criteria.md).

Статуси: **Так** (підтверджено), **Ні** (не виконано, задача повертається), **Частково** (є зауваження), **Очікує** (артефакт ще не здано). На момент підготовки чек-листа команда артефакти ще не здала, тому всі пункти мають статус "Очікує"; документ заповнюється на рев'ю.

| 1.3 | Для slim використовується multi-stage build | читання `Dockerfile.slim` | два етапи (`AS builder` і фінальний), у фінальний переноситься лише встановлене (`COPY --from=builder`), компілятори й кеш лишаються в етапі збірки | AC-03 | Очікує |

| 1.6 | Команда запуску задана в образі | `ENTRYPOINT`/`CMD` у Dockerfile | контейнер запускає інференс без ручних команд усередині | AC-05 | Очікує |

## Стоп-фактори

Будь-який із цих пунктів повертає задачу без подальшого рев'ю:

- slim дає інші top-3 класи, ніж fat (4.4);
- образ не збирається за командами з README на чистій машині (3.1, 3.5);
- у репозиторії або в шарах образу знайдено секрети;
- залежності без зафіксованих версій (2.2): результат не можна відтворити через місяць.

## Висновок рев'ю

Поточний стан: артефакти команди ще не здані, рев'ю не проводилось. Чек-лист погоджено як інструмент приймання, він використовується на демо від команди. Після рев'ю тут фіксується: дата, хто перевіряв, кількість пунктів зі статусом "Так / Частково / Ні", рішення (прийнято / повернено із зауваженнями).
