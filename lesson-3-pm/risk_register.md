# Risk Register: поставка моделі класифікації зображень у Docker-образах

Ймовірність і вплив: Low / Medium / High. Оцінки зроблено на старті задачі, до здачі артефактів; переглядаються після рев'ю за [`docker_image_review.md`](docker_image_review.md) і [`optimization_report_review.md`](optimization_report_review.md).

## Реєстр

| ID | Ризик | Ймовірність | Вплив | Mitigation | Owner |
|---|---|---|---|---|---|
| R-01 | Image працює локально, але не готовий до staging (інша архітектура процесора сервера, залежність від локальних шляхів, відсутня перевірка стану) | High | High: зрив терміну пілоту, повторна ітерація | Критерії AC-04, AC-05, AC-09 перевіряє QA на чистій машині; на staging розгортається той самий образ з тим самим тегом, без перезбирання; контрольний прогін тестового набору після розгортання | DevOps |
| R-02 | Slim image дає інший prediction, ніж fat | Low | High: клієнт бачить хибні варіанти, оптимізація шкодить продукту | Один `requirements.txt` з точними версіями, один `app/inference.py`, однаковий `model.pt` з контрольною сумою; порівняння на 3-5 зображеннях (AC-08); правило рішення: slim не приймається до виправлення | AI/ML Engineer |
| R-03 | Несумісність версій Python, `torch` або `torchvision` | Medium | High: образ не збирається або падає на старті | Мінімальна пара для Python 3.13: `torch 2.6.0` і `torchvision 0.21.0` (перевірено за PyPI); пакети беруться лише в підтвердженій парі, версії фіксуються через `==` | AI/ML Engineer |
| R-04 | Зайві файли потрапляють у build context (`.git`, ноутбуки, дані, `.env`) | High | Medium: повільна збірка, роздутий образ, можливий витік секретів | `.dockerignore` обов'язковий (AC-12), перевірка вмісту slim (AC-11), `COPY` лише потрібних каталогів, а не всього репозиторію | AI/ML Engineer |
| R-05 | Немає README з командами | Medium | Medium: результат не відтворює ніхто, крім автора; залежність від однієї людини | README обов'язковий deliverable; AC-09: QA, який не писав код, відтворює результат лише за README | AI PM |
| R-06 | Немає порівняння fat і slim | Medium | Medium: оптимізацію неможливо оцінити, рішення про staging приймається наосліп | `report.md` обов'язковий (AC-10); без нього AI PM не підписує Definition of Done | AI PM |
| R-07 | Production-секрети потрапили в Compose або в репозиторій | High | High: витік доступу до робочих систем, компрометація інфраструктури | `.env` у `.gitignore`, у репозиторії лише `.env.example` з тестовими значеннями; рев'ю `compose.yaml` і історії комітів; при витоку негайна заміна секрету | DevOps |
| R-08 | Локальний стенд підключається до production DB або queue | Low | High: тестові дані потрапляють у робочу базу, можлива втрата даних | Хости в `.env.example` лише імена сервісів Compose; робоча мережа недоступна з локального стенду; пункт 10 чек-листа Compose як стоп-фактор | DevOps |
| R-09 | Немає версії model artifact | Medium | High: неможливо довести, яка саме модель працює на сервері, і повторити результат | README фіксує архітектуру, варіант ваг, версії бібліотек і контрольну суму `model.pt` (AC-15); тег образу `1.0` пов'язаний з цією версією моделі | AI/ML Engineer |
| R-10 | Image завеликий для швидкого delivery (потрапили бібліотеки CUDA замість CPU-only) | High | Medium: повільний CI/CD, довге розгортання, економія лише 10-15% | CPU-only збірка `torch` у slim (AC-13), multi-stage, `--no-cache-dir`; поріг зменшення щонайменше 30% (AC-14) | DevOps |

## Пріоритет

Критичну увагу зосереджено на ризиках з високим рівнем впливу (High impact). Першочерговий фокус команди спрямовано на R-01 (неготовність образу до staging) та R-07 (витік секретів), які мають найвищу комбінацію ймовірності та шкоди. Навіть при низькій імовірності (R-02, R-08) ризики з високим впливом залишаються безумовними стоп-факторами приймання.

## Позиція AI PM

Для мене як керівника проєкту найголовніше: уникнути реалізації високих ризиків (High impact). Високі ризики здатні повністю зупинити реліз, призвести до витоку конфіденційних даних або зірвати перехід на тестове середовище. Середні ризики (Medium) також приносять неприємності та затримки, але вони не є фатальними й вирішуються в робочому порядку без загрози зриву всього продукту. Тому всі заходи контролю та валідації я насамперед спрямовую на повне блокування критичних загроз.
