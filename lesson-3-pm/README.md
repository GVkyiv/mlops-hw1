# Пакет документації AI Project Manager: Контейнеризація та оптимізація ML-моделі (ДЗ №1)

Цей репозиторій містить управлінський пакет документації для контролю доставки моделі комп'ютерного зору (MobileNetV2) у складі чат-бота онлайн-магазину. Робота охоплює повний цикл PM-контролю: від бізнес-вимог і технічного завдання до критеріїв приймання, технічного рев'ю контейнерів, реєстру ризиків та звіту для стейкхолдерів.

## Короткий контекст

Команда готує сервіс розпізнавання товарів за фотографіями клієнтів у чат-боті підтримки онлайн-магазину "ДімМаркет". Модель класифікує зображення та повертає три найбільш вірогідні категорії (top-3 prediction). Для надійної доставки інженерна команда збирає два Docker-образи:
1. `ml-infer-fat:1.0`: базовий образ на повному `python:3.13` (еталон працездатності та результату).
2. `ml-infer-slim:1.0`: оптимізований образ на `python:3.13-slim` із застосуванням multi-stage build та CPU-only коліс PyTorch.

Головний принцип AI PM: оптимізація розміру образу не має права погіршити чи змінити передбачення моделі.

## Questions to AI/ML Team

Перелік обов'язкових запитань до команди під час постановки та приймання задачі:

1. Який фінальний model artifact використовується та яка його контрольна сума (SHA-256)?
2. Яка конкретна версія чи варіант ваг моделі зафіксований (наприклад, `MobileNet_V2_Weights.DEFAULT` чи `IMAGENET1K_V1`)?
3. Який точний формат очікується на вході (роздільна здатність, RGB) та на виході (структура JSON або текстовий вивід top-3)?
4. Чи підтверджена сумісність обраного стеку з базовим образом `python:3.13`?
5. Чи підтверджена сумісність та наявність готових коліс під `python:3.13-slim`?
6. Чи сумісні між собою та з Python 3.13 обрані версії `torch` (>=2.6.0), `torchvision` (>=0.21.0) та `pillow` (>=11.0.0)?
7. Чи присутній файл `.dockerignore` у корені репозиторію і що саме він виключає?
8. Чи збігаються результати інференсу (top-3 класи та порядок) для fat і slim на фіксованому наборі з 3-5 зображень?
9. Чи підготовлений звіт `report.md` із зафіксованими вимірами розміру, часу збірки та порівнянням виводу інференсу?
10. Чи містить `README.md` точні команди build і run для обох образів, які відтворюються на чистій машині?
11. Чи потрібен Docker Compose для локального стенду на поточному етапі (згідно зі Scope, це наступний крок)?
12. Чи гарантовано відсутні секрети, паролі та файли `.env` у репозиторії, шарах образу та Compose-файлах?
13. Чи використовується при встановленні `torch` у slim-образі індекс з CPU-only колесами для запобігання підтягуванню CUDA?

## Команди для перевірки артефактів

Після здачі коду інженерною командою перевірка виконується такими командами:

```bash
# 1. Перевірка наявності .dockerignore
cat .dockerignore

# 2. Збірка обох образів
docker build -f Dockerfile.fat -t ml-infer-fat:1.0 .
docker build -f Dockerfile.slim -t ml-infer-slim:1.0 .

# 3. Перевірка розмірів образів
docker images | grep ml-infer

# 4. Перевірка відсутності CUDA у slim-образі
docker run --rm --entrypoint python ml-infer-slim:1.0 -c "import torch; print('CUDA available:', torch.cuda.is_available(), 'CUDA version:', torch.version.cuda)"

# 5. Тестовий інференс на однаковому зображенні
docker run --rm -v "$(pwd)/tests/images:/data:ro" ml-infer-fat:1.0 /data/lamp.jpg
docker run --rm -v "$(pwd)/tests/images:/data:ro" ml-infer-slim:1.0 /data/lamp.jpg

# 6. Перевірка історії шарів та відсутності секретів
docker history ml-infer-slim:1.0
```
