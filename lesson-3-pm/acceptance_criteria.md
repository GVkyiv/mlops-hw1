# Acceptance Criteria: образи `ml-infer-fat:1.0` і `ml-infer-slim:1.0`

Кожен критерій відповідає на питання: "Як ми зрозуміємо, що задача виконана правильно?" Для кожного вказано, як саме перевіряємо і хто. Команди наведено для Linux/macOS або Git Bash; точний спосіб передачі тестового зображення команда фіксує в `README.md`, нижче приклад.

Пов'язані документи: задача [`ai_ml_team_task.md`](ai_ml_team_task.md), технічний чек-лист [`docker_image_review.md`](docker_image_review.md).

## Обов'язкові критерії

| ID | Критерій | Як перевіряємо | Хто |
|---|---|---|---|
| AC-01 | fat image використовує `python:3.13` | `grep '^FROM' Dockerfile.fat` повертає `FROM python:3.13` | DevOps |
| AC-02 | slim image використовує `python:3.13-slim` | `grep '^FROM' Dockerfile.slim`: фінальний `FROM` це `python:3.13-slim` | DevOps |
| AC-03 | slim image зібраний через multi-stage build | у `Dockerfile.slim` щонайменше два `FROM`, перший з іменем етапу (`AS builder`), у фінальному етапі є `COPY --from=builder` | DevOps |
| AC-04 | обидва образи збираються без помилок | `docker build -f Dockerfile.fat -t ml-infer-fat:1.0 .` і `docker build -f Dockerfile.slim -t ml-infer-slim:1.0 .` завершуються з кодом 0 на чистій машині | QA |
| AC-05 | обидва образи запускаються через `docker run` | приклад: `docker run --rm -v "$(pwd)/tests/images:/data:ro" ml-infer-slim:1.0 /data/lamp.jpg`, контейнер відпрацьовує і завершується з кодом 0, без помилок у виводі | QA |
| AC-06 | для fat і slim використовується однаковий test input | обидва образи запускаються на тих самих файлах з `tests/images/`; контрольні суми файлів (`sha256sum tests/images/*`) наведені в `report.md` | QA |
| AC-07 | inference повертає top-3 prediction | для кожного зображення три рядки "клас: ймовірність %", впорядковані за спаданням, сума трьох ймовірностей не більша за 100% | QA |
| AC-08 | результат inference у fat і slim збігається | для кожного тестового зображення однакові три класи в однаковому порядку; різниця ймовірностей кожного класу не більша за 0,1 відсоткового пункту; повторний запуск того самого образу дає той самий вивід | QA, підтверджує AI PM |
| AC-09 | README містить команди для build/run | QA, який не писав код, виконує команди з `README.md` послідовно і отримує результат без додаткових кроків і запитань до розробника | QA |
| AC-10 | `report.md` містить порівняння fat і slim | у звіті таблиця: розмір образу, кількість шарів, час збірки, час запуску, вивід інференсу обох образів, пояснення різниці | AI PM |
| AC-11 | у slim image немає зайвих файлів | `docker run --rm --entrypoint ls ml-infer-slim:1.0 -la /app`: лише код застосунку і модель, без `.git`, ноутбуків, `__pycache__`, тестових даних, `Dockerfile*`; `docker run --rm --entrypoint pip ml-infer-slim:1.0 list` без Jupyter, pytest, лінтерів | DevOps |
| AC-12 | у репозиторії є `.dockerignore` | файл є в корені і виключає щонайменше `.git`, `__pycache__`, `*.ipynb`, `.env`, віртуальні оточення | DevOps |

## Додаткові критерії

Ці пункти не названі в завданні прямо, але без них обов'язкові критерії можна формально виконати й отримати непридатний результат.

| ID | Критерій | Як перевіряємо | Хто |
|---|---|---|---|
| AC-13 | у slim встановлена CPU-only збірка `torch` | `docker run --rm --entrypoint python ml-infer-slim:1.0 -c "import torch; print(torch.__version__, torch.version.cuda)"` виводить версію з `+cpu` і `None` | DevOps |
| AC-14 | оптимізація вимірювана | slim щонайменше на 30% менший за fat за `docker images`; якщо менше, у `report.md` пояснено причину. Поріг 30% це емпіричне правило ментора курсу, не галузевий стандарт | DevOps, AI PM |
| AC-15 | версія і джерело моделі задокументовані | `README.md` називає архітектуру, варіант ваг (`MobileNet_V2_Weights...`), версії `torch`/`torchvision`, контрольну суму `model/model.pt` | AI/ML Engineer |
| AC-16 | немає секретів | у репозиторії немає `.env` і ключів; `docker history --no-trunc ml-infer-slim:1.0` не містить токенів і паролів | DevOps |
| AC-17 | модель не завантажується з інтернету на старті | `docker run --rm --network none ...` на тестовому зображенні дає той самий результат, що й з мережею | QA |

## Правило рішення

- Якщо не пройдено AC-08, slim не приймається: розбіжність результату означає, що оптимізація зламала модель. До виправлення для локальної перевірки й демонстрації використовується fat.
- Якщо не пройдено AC-14, slim формально приймається, але задача повертається на оптимізацію з поясненням у `report.md`.
- Решта критеріїв обов'язкові без винятків.

## Definition of Done

Задача вважається виконаною (Definition of Done), якщо одночасно:

1. Будь-який член команди може клонувати репозиторій, виконати команди з `README.md`, зібрати fat і slim image, запустити inference на однаковому наборі тестових зображень і побачити однаковий результат prediction.
2. Пройдено всі критерії AC-01...AC-12 і AC-13, AC-15, AC-16, AC-17; AC-14 пройдено або обґрунтовано в `report.md`.
3. Результат перевірив QA, який не брав участі в розробці.
4. `report.md` з порівнянням і еталонним виводом інференсу додано в репозиторій.
5. Образи мають теги `ml-infer-fat:1.0` і `ml-infer-slim:1.0`, зміни злиті в основну гілку.
6. AI PM переглянув `report.md`, заповнив [`optimization_report_review.md`](optimization_report_review.md) і прийняв рішення щодо переходу на staging.
